# fx-watch

Сервис регулярно забирает данные из открытого источника, хранит их так, что видна вся история
изменений, и следит за тем, чтобы данные не сломались незаметно.

**Живой стенд:** https://antonov-ai.ru/agents/fxwatch/ - работает прямо сейчас, цифры на дашборде
приходят из этого сервиса.

---

## Если коротко и без технических слов

Есть источник, который каждый день публикует числа - в данном случае Банк России и курсы валют.
Сервис сам ходит за этими числами, складывает их к себе и делает четыре вещи, которых обычно
не делают, когда просто «выгружают данные»:

1. **Ничего не перезаписывает.** Каждое полученное значение ложится новой строкой с отметкой,
   когда оно пришло. Поэтому видно не только каким был курс, но и что сервис знал о нём в любой
   прошлый день. Если источник задним числом поправил своё же число, обе версии останутся.

2. **Не теряет данные, когда источник недоступен.** Если источник не ответил, сервис подождёт
   и попробует снова. Если источник лежал два дня, сервис потом сам догонит пропущенное:
   он знает, за какие даты у него нет данных.

3. **Замечает, что с данными что-то не так.** Пустой ответ, три валюты вместо сорока,
   отрицательный курс, скачок в десять раз, значение, которое перестало меняться. Подозрительная
   запись откладывается в сторону, а остальные сохраняются: одна плохая строка не отменяет весь день.

4. **Ведёт журнал каждого захода.** Через три месяца по этому журналу собирается отчёт, который
   отвечает на вопрос «всё ли было в порядке» цифрами, а не на словах.

Подробное объяснение для нетехнического читателя: [docs/for-non-technical.md](docs/for-non-technical.md).
Список спорных решений и почему они приняты именно так: [DECISIONS.md](DECISIONS.md).

## Запуск

Одна команда, без ключей и учётных записей: оба источника публичные.

```bash
docker compose up -d
```

Через пару минут сервис сам зальёт историю за 90 дней и станет доступен:

| Что | Где |
|---|---|
| Состояние сервиса | http://localhost:8790/api/fxwatch/health |
| Сводка и данные | http://localhost:8790/api/fxwatch/overview |
| Отчёт за 90 дней | http://localhost:8790/api/fxwatch/report.md |
| Документация API | http://localhost:8790/api/fxwatch/docs |

Полезные команды:

```bash
make test      # тесты, сети и базы не требуют
make report    # отчёт за период в reports/latest.md
make seed      # демонстрационные инциденты (синтетические, см. ниже)
make logs      # что делает планировщик прямо сейчас
```

## Источник и стек

**Основной источник:** Банк России, `cbr.ru/scripts/XML_daily.asp` - официальные курсы, XML в
кодировке windows-1251, около 44 валют, без ключа и без ограничений на частоту. Выбран по трём
причинам: есть архив по датам, поэтому историю за три месяца можно залить сразу, а не ждать
три месяца; есть выходные и праздники, что даёт естественный случай «значение не меняется, и это
норма»; данные простые, поэтому внимание в решении уходит на устройство, а не на разбор формата.

**Второй источник:** `open.er-api.com` - рыночный курс USD, три валюты, нужен только для сверки.
Два независимых источника ловят класс ошибок, невидимый изнутри одного: технически корректное,
но неверное на порядок значение.

**Стек:** Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2.0, Alembic, APScheduler, httpx,
pytest с respx, Docker Compose, GitHub Actions. Ничего экзотического - задача не требует.

## Как закрыто каждое требование

### Требование 1. Периодичность опроса и её обоснование

Одного интервала здесь не хватает, потому что задачи разные. Расписаний четыре:

| Задача | Когда | Почему так |
|---|---|---|
| Опрос | каждые 30 мин, 11:00-16:00 МСК, пн-пт | ЦБ публикует курс раз в сутки, обычно между 11:30 и 15:30. Опрос идёт короткими попытками внутри окна публикации и прекращается, как только курс за сегодня получен |
| Контрольный опрос | 23:00 ежедневно | ловит публикацию, сдвинувшуюся за пределы окна |
| Перезапрос окна | 03:00 ежедневно, последние 14 дней | см. ниже, закрывает сразу три требования |
| Проверки состояния | каждые 6 часов | им нужна накопленная история, а не один ответ |

Почему не чаще: источник обновляется раз в сутки, более частый опрос не даёт новой информации,
а журнал засоряет. Почему не раз в сутки: единственная попытка может попасть ровно в окно
недоступности источника, и тогда о проблеме мы узнаем через сутки вместо получаса.

**Перезапрос окна на 14 дней** - центральная конструкция решения. Одна задача закрывает три
разных требования: догоняет даты, пропущенные во время простоя (требование 3), обнаруживает
исправления источника задним числом (требование 4) и задаёт границу, после которой период
считается закрытым, а его изменение - уже инцидент, а не норма (тоже требование 4).

### Требование 2. История изменений, а не последнее состояние

Здесь важно различать две истории, и это же различие отвечает на требование 4:

* как менялось **значение** - курс по дням;
* как менялось **наше знание о значении** - что сервис считал верным в каждый момент.

Таблица `observations` хранит обе. Она append-only, в ней никогда не выполняется UPDATE,
и у каждой строки две временные оси: `value_date` - к какой дате относится значение,
`observed_at` - когда мы его получили.

Текущее состояние - это выборка последней версии по каждой дате:

```sql
SELECT DISTINCT ON (source_code, series_key, value_date) ...
ORDER BY source_code, series_key, value_date, observed_at DESC
```

Состояние на прошлый момент - та же выборка с одним дополнительным условием
`observed_at <= :as_of`. Поэтому любой отчёт, сделанный месяц назад, воспроизводится точно
в том виде, в каком он был, и видно, на каких числах он строился. На дашборде это ползунок
«машина времени»: пунктирная линия показывает, что сервис знал на выбранный момент.

### Требование 3. Устойчивость к недоступности, медленным ответам и ошибкам

| Механизм | Как сделано |
|---|---|
| Таймауты | явные на каждую фазу: 5 с на соединение, 15 с на чтение, 30 с на весь запрос |
| Повторы | до 5 попыток, задержка 1-16 с экспоненциально, с джиттером до 40% |
| Что повторяем | сетевые ошибки, таймауты, 5xx, 429. На 4xx **не** повторяем: это наш неверный запрос, а не сбой источника |
| Ограничение частоты | 429 обрабатывается отдельно, пауза берётся из заголовка `Retry-After` |
| Предохранитель | после 4 неудач подряд источник признаётся недоступным на 15 минут, попытки в этот период пишутся в журнал со статусом `skipped` |
| Идемпотентность | повторный запуск за ту же дату безопасен, дублей не создаёт |
| Незавершённые прогоны | если процесс убили в момент сбора, при старте такие записи помечаются неуспешными, а не висят вечно |
| Планировщик | `coalesce` и `misfire_grace_time`: после простоя выполняется одна задача, а не очередь накопившихся |

Отдельно про «не теряет данные». Устойчивость - это не только «не упал». Сервис знает, за какие
даты у него нет данных: если за дату нет наблюдений и не было успешного запроса, это дыра,
и она попадает в очередь на добор. Поэтому после любого простоя история восстанавливается сама.

Второе следствие того же принципа: если из сорока четырёх валют одна сломана, прогон не
откатывается целиком. Сорок три корректных значения сохраняются, сломанное уходит в карантин,
прогон получает статус `partial`. Полный откат означал бы потерю корректных данных из-за
чужой ошибки в одной строке.

### Требование 4. Источник отдаёт разные значения за один и тот же период

**Решение: не перезаписываем и не игнорируем, а версионируем.**

Механически это один уникальный индекс:

```
UNIQUE (source_code, series_key, value_date, payload_hash)
```

где `payload_hash` - отпечаток самого значения. Отсюда следует всё остальное:

* источник повторил то же значение - тот же хэш, `ON CONFLICT DO NOTHING`, дубля нет;
* источник вернул другое значение - другой хэш, ложится новая строка, обе версии сохранены.

Никакой отдельной логики сравнения не требуется, и повторный сбор нельзя случайно сделать
разрушительным.

Почему не другие варианты:

* **перезаписывать последним значением** - теряется факт исправления. Отчёт, построенный вчера,
  становится невоспроизводимым, и на вопрос «почему в прошлом отчёте было другое число»
  ответить нечем;
* **игнорировать изменения после первой записи** - теряются настоящие исправления источника,
  в базе навсегда остаётся заведомо неверное значение.

Поверх версионирования два порога:

* **порог значимости** (0.05%): расхождение меньше - это шум округления формата, версия
  записывается, но тревога не поднимается. Иначе журнал заполнится «изменениями» в восьмом знаке;
* **окно закрытия периода** (14 дней): пересмотр внутри окна - штатное поведение источника,
  пересмотр старше - помечается как поздняя ревизия и попадает в отчёт отдельно. Без такой
  границы нельзя отличить нормальное уточнение от подозрительного переписывания истории.

Текущая витрина всегда отдаёт последнюю известную версию. Все предыдущие остаются доступными
через `/history` и через `as_of`.

### Требование 5. Обнаружение проблем с данными

Восемь правил, все в одном файле [`quality/rules.py`](src/fxwatch/quality/rules.py) - список того,
что считается нормальными данными, должен читаться целиком, а не собираться по коду.

| Уровень | Проверка | Что ловит | Реакция |
|---|---|---|---|
| Ответ | `response_payload` | пустое или обрезанное тело при формальном HTTP 200 | блокирует |
| Ответ | `completeness` | пришло 3 ряда вместо 44 | блокирует |
| Ответ | `reported_date` | дата в ответе не совпала с запрошенной | информация |
| Значение | `value_range` | ноль, отрицательное, нечисловое, абсурдно большое | карантин |
| Значение | `jump` | скачок больше 10% - предупреждение, больше 30% - карантин | по порогу |
| История | `freshness` | данные перестали поступать дольше 36 часов | тревога |
| История | `stale_series` | значение не менялось 3 рабочих дня подряд | предупреждение |
| История | `cross_source` | расхождение с независимым источником больше 5% | предупреждение |

Три решения внутри этой таблицы стоит отметить отдельно.

**Календарь рабочих дней выводится из данных, а не берётся из библиотеки.** Без календаря
проверка застоя срабатывала бы каждую субботу: курс ЦБ в выходные не меняется по определению.
Готовый производственный календарь РФ - это внешняя зависимость, которая устаревает к каждому
новому году и к каждому переносу выходных. Вместо этого используется поведение самого источника:
если за дату запрос прошёл успешно, но данных нет, значит день нерабочий. Побочная польза:
из того же механизма получается список дыр в истории.

**Несовпадение дат - это информация, а не ошибка.** Запрос выходного дня возвращает курс
предыдущего рабочего дня, и значения записываются под датой из ответа. Ошибкой было бы
обратное: молча записать их под запрошенной датой и получить фиктивные выходные в истории.

**Отсутствие данных для сравнения даёт `skip`, а не `pass`.** Если сравнивать не с чем,
проверка отмечается пропущенной. Зелёная галочка, за которой ничего не стоит, хуже честного
пропуска: она создаёт ложную уверенность.

Порог полноты задаётся источником, а не общей настройкой: у ЦБ норма около 44 рядов, у источника
для сверки - ровно три. Единый порог помечал бы штатный ответ второго источника как сбой.
Эту ошибку я и допустил в первой версии, она нашлась на первом же живом прогоне.

### Требование 6. Сервис проработал три месяца без присмотра

Ключевое различение: **«сервис жив» и «данные корректны» - разные утверждения, и первое
не доказывает второе.** Процесс может исправно подниматься, ходить в сеть и писать в базу,
полгода складывая туда мусор. Поэтому отчёт отвечает не на вопрос об аптайме, а на четыре других.

**1. Покрытие.** За сколько ожидаемых рабочих дней данные реально есть. Главная метрика:
если она ниже 100%, отчёт называет недостающие даты поимённо.

**2. Инциденты.** Неудачные прогоны сгруппированы в события с длительностью и признаком
восстановления. «28 упавших прогонов» не говорит ничего, «два инцидента по четыре часа,
оба восстановились сами, данные добраны» - говорит.

**3. Ревизии.** Сколько значений источник менял задним числом, насколько сильно, какие
из них вышли за окно закрытия периода.

**4. Качество.** Какие проверки не проходили, что попало в карантин, что осталось неразобранным.

Что для этого заложено в само решение:

* таблица `ingest_runs` - каждое обращение к источнику: время, статус, код ответа, число попыток,
  длительность, сколько строк получено, записано, оказалось ревизиями, ушло в карантин;
* **версия кода в каждом прогоне** - через три месяца это единственный способ отличить
  «источник стал вести себя иначе» от «мы сами задеплоили изменение»;
* сырые ответы хранятся 30 дней в сжатом виде: если выяснится, что парсинг был неверным,
  его можно переиграть на сохранённых данных;
* дедупликация тревог по ключу: повторное срабатывание того же условия обновляет счётчик,
  а не шлёт новое сообщение. Без этого за три месяца пришло бы несколько сотен одинаковых писем,
  и их перестали бы открывать - формально мониторинг есть, фактически нет;
* **отметки живости задач с обратной логикой**: тревогу вызывает не событие, а его отсутствие.
  Задача, которая тихо перестала запускаться, иначе неотличима от задачи, у которой всё хорошо;
* отчёт одной командой: `make report` или `GET /api/fxwatch/report.md`.

Пример готового отчёта: [reports/](reports/).

## Про демонстрационные инциденты

Курсы в базе настоящие - это архив Банка России.

Часть записей журнала синтетическая: два сбоя источника, одна ревизия, одно срабатывание проверки
застоя и один битый ответ. Их добавляет [`scripts/seed_incidents.py`](scripts/seed_incidents.py).

Причина прямая: отчёт, в котором все показатели идеальны, ничего не доказывает - непонятно,
механизмы действительно работают или просто ни разу не сработали. Все такие записи помечены
версией кода `demo-seed` и отделяются одним запросом:

```sql
DELETE FROM ingest_runs WHERE code_version = 'demo-seed';
```

Ревизия при этом сделана аккуратно: в историю добавляется **более ранняя** версия значения,
поэтому текущая витрина остаётся точной копией данных ЦБ.

Отдельно стоит отметить, что одно срабатывание в отчёте настоящее: проверка `jump` поймала
реальное движение боливиано на 28% за день. Порог блокировки - 30%, поэтому данные были приняты
с предупреждением, а не отброшены. Ровно то поведение, ради которого пороги разведены.

### Схема данных

| Таблица | Назначение |
|---|---|
| `observations` | append-only наблюдения, две временные оси, уникальность по хэшу значения |
| `ingest_runs` | журнал каждого обращения к источнику |
| `revisions` | события изменения ранее полученных значений |
| `raw_payloads` | сырые ответы в сжатом виде, хранение 30 дней |
| `quality_checks` | результаты проверок |
| `quarantine` | отбракованные записи с причиной |
| `alerts` | тревоги с дедупликацией по ключу |
| `source_state` | состояние предохранителя |
| `heartbeats` | отметки живости регулярных задач |

Плюс две вьюхи: `rates_current` - последняя известная версия каждого значения,
`rates_versions` - сколько раз источник менял мнение по каждой дате.

### Сколько это весит

44 валюты, около 250 рабочих дней в году, плюс запас на ревизии - примерно 11 500 строк
наблюдений в год. Журнал прогонов - около 35 000 строк в год. С индексами это порядка 50 МБ
в год, сырые ответы чистятся по расписанию. Расчёт приведён здесь потому, что вопрос
«что будет с базой через три месяца» - часть требования 6, а не отдельная тема.

### Как подключается новый источник

Один класс с методом `fetch`, возвращающий список `DataPoint`. Всё остальное - повторы,
идемпотентность, история ревизий, проверки, карантин, журнал, отчётность и дашборд -
переиспользуется без изменений. Пример с комментариями о том, что добавится в реальной
интеграции с маркетплейсом (авторизация, пагинация, лимиты, асинхронные отчёты):
[`sources/marketplace_stub.py`](src/fxwatch/sources/marketplace_stub.py).

Для сервиса тема данных не важна: «курс валюты на дату» и «цена товара на дату» - одна и та же
структура, и требования про историю, ревизии и контроль качества закрываются для них одинаково.

## Тесты

37 тестов, база и сеть не нужны: ответы источников подменяются фикстурами и `respx`,
поэтому CI не зависит от доступности ЦБ.

```bash
make test        # в контейнере
pytest -q        # локально, после pip install -e ".[dev]"
```

Что покрыто:

* разбор реального формата ЦБ, включая фикстуры в windows-1251;
* нормализация по номиналу: иена котируется за 100 единиц, в историю должен попасть курс за одну;
* ответ за выходной день: значения ложатся под датой из ответа;
* битый ответ, пустой ответ, неизвестный корневой элемент;
* одна сломанная валюта не отменяет остальные;
* восстановление после 5xx и таймаута, отказ от повторов на 4xx, соблюдение `Retry-After`;
* отпечаток значения: `78.5` и `78.50` не создают ложную ревизию, а изменение в восьмом знаке создаёт версию;
* пороги проверок, включая то, что порог полноты принадлежит источнику.
